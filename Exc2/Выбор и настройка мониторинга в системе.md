# Выбор и настройка мониторинга в системе

### Анализ текущей системы мониторинга

Сайт подключён к Яндекс Метрике. Но с тех пор, как началось оформление заказов через API, данные Яндекс Метрики уже не дают полной картины.

### Мотивация

Добавление мониторинга сделает систему более прозрачной и позволит быстрее обнаруживать наиболее проблемные места в системе и быстро реагировать на них. Это позволит нам исправить текущие проблемы и быстро справиться с новыми вызовами в системе, до того как пользователи массово начнут жаловаться и по итогу терять клиентов и прибыль.

### Выбор подхода к мониторингу

Подход к мониторингу RED хорошо подойдет для мониторинга БД (Shop DB, Messages Queue, MES DB, 3d file storage).
Подход "4 золотых сигнала" хорошо пойдет для мониторинга API (Shop API, CRM API, MES API)

### Метрики

- Number of requests (RPS): позволит оценить как много запросов каждого типа приходят по пользователям. Низкое значение метрики может говорить об узком месте в конкретном сервисе и сигнализировать о потенциальном источнике проблем; labels={"source": "internet_shop" | "CRM" | "MES", status: "INITIATED" | "FILE_UPLOADED" | ..., user: "...", }
- CPU usage in %; позволит оценить насколько трудоемкие операции с точки зрения CPU; При высоком значении можно будет подумать о горизонтальном/вертикальном масштабировании, и (или) оптимизации текущих наиболее трудоемких операций; labels={"source": "internet_shop" | "CRM" | "MES", }
- Memory Utilization; При высоком значении можно будет подумать о вертикальном масштабировании, и (или) оптимизации кода/операций по памяти; labels={"source": "internet_shop" | "CRM" | "MES", }
- Memory Utilization for db instances; При высоком значении можно будет подумать о репликации/шардировании для снижения нагрузки; labels={"source": "shop_db" | "MES_db", }
- Number of connections for db instances; При высоком значении можно будет подумать о репликации/шардировании для снижения нагрузки; labels={"source": "shop_db" | "MES_db", }
- Response time (latency) for API; Позволит оценить наиболее тяжелые запросы по времени и в первую очередь стараться оптимизировать их; labels={"source": "internet_shop" | "CRM" | "MES", status: "INITIATED" | "FILE_UPLOADED" | ..., }
- Size of storage (S3|shop_db|MES_db); Позволит отслеживать когда будет критически высокие значения используемой памяти и стоит своевременно увеличить доступное пространство для хранения. Также высокое используемое дисковое пространство при использовании в облаке может может много стоить, если за ним не следить; labels={"source": "S3"|"shop_db"|"MES_db"}
- HTTP response status counts for API; Позволит мониторить количество ошибок и понимать по каким причинам (каким кодом) наибольшее количество ошибок - например timeout. labels={"source": "internet_shop" | "CRM" | "MES", status: "INITIATED" | "FILE_UPLOADED" | ..., http_status: 440 | 500 | 200 | ..., }
- Number of message in flight in RabbitMQ; Позволит отслеживать загруженность очереди;
- Number of dead-letter-exchange letters in RabbitMQ; Позволит определить наиболее частые ошибки и причины связанные с взаимодействием с RabbitMQ.

### План действий

1. Настроить Prometheus:
    - Развернуть инстанс Prometheus.
    - Настроить на каждом сервисе (API, DataBases, RabbitMQ, ...) exporter для сбора метрик через Prometheus.
2. Настроить Grafana для визуализации метрик:
    - Установить Grafana и подключить к Prometheus.
    - Натсроить dashboards с метриками.
3. Настроить alerting для высоких/экстримальных значений метрик
